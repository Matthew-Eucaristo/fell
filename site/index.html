Your agents left worktrees behind.
Cut them down. Lose nothing.

Claude Code, Codex, Cursor, Conductor and friends give every chat, session or subagent its own git worktree: a full checkout with its own node_modules and build output, scattered across half a dozen places, often on detached HEADs that git branch never shows. fell finds them all, shows exactly what is in each one, and cuts them down to the Trash. Nothing is deleted permanently, and nothing an app still uses is touched.

Why it exists

The leak is real. So are the bad cleanups.

Every parallel session gets a full checkout, and guides for parallel agents put that at 300–500 MB of dependencies per worktree. Vendor cleanups fail both ways: some never run, others delete live work and git-ignored files without a trace. Reported in public issue trackers:

764Claude Code subagent worktrees, all detached HEADs: ~36 GB, 220 MB left free ~200 GBacross 22 Claude Code worktrees with .worktreeinclude full copies 556Claude Code Workflows isolation lanes from 18 runs in two weeks ~140 GBfrom ~22 Cursor parallel-agent worktrees in a week 2.9 GBof generated images and ignored databases deleted by a pool cleanup's git worktree remove --force. Nothing went to the Trash. live workdiscarded by another session's cleanup, which checked git state but not whether the worktree was in use

Sources and per-tool research: docs/design.md. fell's rules come from these incidents.

Which worktrees it knows

Every agent keeps them somewhere else. fell checks all of it.

It walks your code roots and every known agent location, asks git (git worktree list --porcelain), and labels each worktree with the tool that made it. When an app still keeps its own record, fell only strips it and tells you how that app removes it.

The evidence for each

A clean git status is not enough.

A worktree can hold git-ignored secrets, be in use by a process, be locked by a session, or hold commits no branch shows. fell checks all of it, per worktree:

  • Size, and how much is rebuildable: node_modules, .venv, target, build output.
  • Commits on no remote, detached HEADs included, and commits that exist only in that worktree: HEAD, its reflog, its per-worktree refs.
  • Uncommitted changes and git-ignored secrets and data: .env*, keys, local databases.
  • Last activity, from the last commit, git's own record or file changes.
  • Liveness: processes working inside it, locks naming a running session, the owning app.
  • Locks, keep markers, missing checkouts and orphaned ones.

Two ways to cut

Strip what rebuilds. Retire what is done. Both reversible.

strip

Keep the worktree, drop its weight

Moves rebuildable artifacts to the Trash and keeps the checkout. The safe answer for a worktree that still holds work. Only directories that match the catalog and that git ignores, with nothing tracked inside and no repository below, never through a symlink.

DirectoryComes back with
node_modules .next .nuxt .svelte-kit .turbo dist build …npm / pnpm / yarn / bun install, the next build

A symlinked node_modules (Claude Code's worktree.symlinkDirectories) is never followed: it belongs to the main checkout.

retire

Save a rescue folder, then let it go

Writes a rescue folder to the Trash first, then moves the checkout to the Trash and lets git worktree prune drop git's record. Branches are kept. Never git worktree remove, which deletes ignored files permanently.

# put it back
git -C ~/dev/shop fetch ~/.Trash/fell-rescue-…/commits.bundle \
    HEAD:refs/heads/fell-rescue/agent-a3f9
git -C ~/dev/shop worktree add ~/dev/shop-restored fell-rescue/agent-a3f9

The bundle is verified with git bundle verify and built in a throwaway repository, so no ref is added to yours. Emptying the Trash is your explicit act of forgetting.

Safety model

A cleaner is only as good as what it refuses to do.

Every action re-reads the worktree right before acting and checks it against what you saw. The checks live in internal/clean, the only code that changes anything.

  • ● safe nothing would be lost; retire allowed
  • ▲ caution allowed; something is saved to the rescue folder or worth a look
  • ■ protected retire needs force or unlock, or is blocked
  • ◉ live its app or session is running; fell will not touch it

⎔Pinned to the scan

A fingerprint covers HEAD, branch, uncommitted changes, locks, app tracking, ignored secrets and the directory's identity. Anything changed since the scan, and the action is refused.

◉Live means hands off

A Claude Code lock naming a running process (PID and start time checked), a Claude Desktop lease, the owning app running, or an agent working inside. Not even --force acts on it.

⌘The owner's way, not ours

A worktree an app still tracks is never retired; fell shows how that app removes it. Vendor state is read, never written, and an unknown format counts as tracked.

⛬Never lose work

Dirty, in use, or holding commits found nowhere else: retire refuses without --force, and even then bundles the commits, saves a patch and copies ignored secrets first.

⑂Git's documented removal

Checkout to the Trash, then git worktree prune, only when its dry run would drop nothing but this worktree's entry. Never deletes branches, never edits .git internals.

⊘Guards

Main checkouts and bare repos are never items. No symlinks, no home folder or its ancestors, no tracked or unignored artifacts, no repository hidden below one.

⌫Trash by default

/usr/bin/trash or Finder on macOS, the freedesktop.org home trash on Linux. --permanent exists only for strip. Locked worktrees need --unlock.

◌Read-only scanning

git runs with --no-optional-locks and core.fsmonitor=false, so a scan doesn't even refresh an index. --dry-run, --list, --json and scan change nothing.

Press r on the protected Claude Code lane in the demo above: the confirmation shows what would run, what is saved, and what is refused and why. f forces it, and the only-here commit is bundled.

Honest numbers

Measured from the disk, not assumed.

Worktrees share a lot: pnpm hard links, APFS clones, local snapshots. Adding up du overstates what removal frees, so fell keeps the numbers apart.

  • Allocated blocks, hard links once. A file hard-linked several times counts once.
  • Shared is not freeable. Hard links reaching outside the worktree and, on macOS, blocks APFS shares with clones or snapshots (each file's private size, ATTR_CMNEXT_PRIVATESIZE) are reported as shared.
  • Freed space is measured. After acting, fell reports the change in free disk space.
  • The Trash still holds it. Moving to the Trash frees nothing until you empty it, and Time Machine local snapshots can hold space a while longer. fell says so instead of claiming a number.
  • Known blind spot. Btrfs and XFS reflinks on Linux are not visible and count in full.

For tools and scripts

A TUI when you look. A contract when you don't.

fell scan --json and fell capabilities --json follow a versioned contract with IDs and fingerprints. fell apply --plan runs a list of {id, fingerprint, action} items and refuses any that changed since the scan. It is how decruft hands worktrees back to fell, and any cleanup tool can adopt the same shape.

Exit codes
0every item done, or a dry run
1error before acting (bad roots, git missing)
2usage error, or an invalid plan
3at least one item refused, none failed
4at least one item failed (partial)
# interactive: ~/dev (or the current dir) + agent locations
fell
# try everything, change nothing
fell --dry-run
# other roots; table and exit
fell ~/code ~/work
fell --list
# machine-readable scan, never changes anything
fell scan --json
# one worktree, by ID or path
fell strip wt-ac80840e6477
fell retire --dry-run ~/dev/shop/.claude/worktrees/agent-b81d
# strip every safe worktree, through a plan
fell scan --json \
  | jq -r '.items[] | select(.safety.level=="safe")
      | {id, fingerprint, action:"strip"}' \
  | jq -s '{schema_version:1, items:.}' \
  | fell apply --plan - --dry-run

Questions

Fair questions.

Can it lose my work?

Retire refuses worktrees that are dirty, in use, or hold commits found nowhere else, unless you pass --force. Even then it first bundles those commits, saves a patch of uncommitted changes and copies ignored secrets into a rescue folder, and everything goes to the Trash. When fell can't tell what would be lost, it treats the worktree as protected. Worktrees with submodules are never retired.

Why not just git worktree remove?

It deletes the checkout permanently, git-ignored files included (your .env, a local database), and with --force dirty ones too. On a detached HEAD, the commits only that worktree held are orphaned. git documents another path: delete the directory, then git worktree prune. fell takes that path, with the Trash instead of delete.

What about worktrees Codex, Cursor or Claude Desktop manage?

fell shows them, can strip their rebuildable artifacts while the app isn't running, and never retires them, even with --force. Each one carries the owner's official way to remove it, because the app keeps its own record and may want to restore it.

I retired a worktree. Why didn't free space go up?

Because it is in the Trash, where Put Back restores it. Empty the Trash to reclaim the space; Time Machine local snapshots may hold it a while longer. fell reports the measured change rather than a promise.

Does it write anything, or phone home?

No config, cache, log or state files, and no network requests. A short-lived staging folder exists only during a retire. JSON output writes paths under your home as ~/…. This page loads nothing from third parties either.

My agent tool isn't listed.

Open a feature request with where it puts worktrees and how it removes them. Until then, worktrees of repositories under your roots still show up, attributed to git. Folders another tool is in the middle of deleting are left alone.

I found a bug that touches the wrong thing.

That is a security issue. Please report it privately through GitHub Security Advisories, not a public issue.
